# Новая автоматизация

Ядро уже умеет главное: узнаёт об изменениях (вебхук + опрос), знает предыдущий статус
(`event.previous_state`), не запускает одно и то же дважды, повторяет сбои, шлёт алерты,
уважает dry-run. Автоматизация — это только «надо ли» и «что сделать». Не пиши свою очередь,
планировщик или HTTP-клиент.

Устройство — `docs/ARCHITECTURE.md`, интерфейс — docstring `hub/automations/__init__.py`.
Факты об API — скил `moysklad-api`.

## 0. Может, хватит конфига

Готовые классы часто закрывают задачу одной записью в `config.yaml` с `uses:`:

| Нужно | uses |
|---|---|
| документ покупателю по статусу | `send_document` (`send_upd` для УПД) |
| сообщение людям: статус, создание, переход A → B | `notify` |
| статус заказа по отгрузке | `sync_order_state` |
| поля и статус контрагента | `counterparty_fields` |
| сводка по расписанию | `daily_digest` |

Подходит — добавь запись, `python -m hub check`, готово. Новый код — только если не хватает.

## 1. Договорись о четырёх вещах

Спроси, если из запроса не ясно. От этого зависит, не уйдёт ли клиенту что-то дважды:

1. **Когда.** Тип, статус, переход, создание, юрлицо, доп. поле, время суток.
2. **Сколько раз.** Ключ `key()`: раз на сущность, раз на вход в статус (`id:state`),
   раз на каждое изменение (`id:updated`).
3. **Что и куда.** Документ или текст; каналы.
4. **Как отметить.** Доп. поле в МойСклад (`mark_field`) или статус после — или достаточно журнала.

## 2. Напиши модуль

Скопируй `hub/automations/_template.py` в `hub/automations/<имя>.py`:

- `kind` — уникальное имя класса; `entities` — с какими типами работает.
- Все параметры с безопасными значениями — в `defaults`. Имя параметра не должно совпадать
  с атрибутом класса: хаб это проверит. Неизвестный параметр в config.yaml хаб отвергнет при старте.
- `validate()` — проверь параметры, чтобы ошибка конфига вылезла при старте.
- `wants()` — только проверки по загруженной сущности, без запросов в API.
  Переход статуса — `event.state_changed(obj.state)` и `event.previous_state`.
- `run()` — работа. Наружу только через `ctx.channels`, записи в МойСклад только через
  `ctx.set_state()` / `ctx.set_fields()`: тогда dry-run и журнал работают сами. Чтение —
  `ctx.ms` и `hub.moysklad.fields`.
- `raise Skip("почему")` — делать нечего, повторять бессмысленно. Любое другое исключение —
  повтор по расписанию.
- Несколько каналов — каждый в `ctx.step_done/mark_step` с ключом
  `ctx.run_key(self, self.key(obj, None))`, как в `send_document.py`.
- Плановая автоматизация: `scheduled = True`, `slot(now)` и `run_scheduled(ctx, slot)`,
  как в `daily_digest.py`.

Новый тип документа — класс в `hub/entities.py`, строка в `TYPES` и `ALIASES`. Опрос, вебхуки,
REST и статусы для него заработают сами. Научи `tests/fake_moysklad.py` этому типу.

## 3. Тест на поддельном МойСклад

`tests/test_<имя>.py` по образцу `tests/test_automations.py`: фикстуры `fake` и `make_hub`,
`fake.add_order / add_demand / add_counterparty / add_field / set_state`, `webhook(...)`,
`await hub.tick()`, проверки по `hub.channels.*` и `fake.db`. Минимум:
срабатывает когда надо, не срабатывает когда не надо, второй раз не делает, сбой уходит
в повтор, dry-run ничего не пишет.

```bash
python3 -m pytest -q && ruff check .
```

## 4. Включи и обкатай

Запись в `config.yaml` с `enabled: true`, затем `python -m hub check`. На реальной записи —
`python -m hub run <имя> <номер>` при `HUB_DRY_RUN=1`: покажет, что ушло бы и что записалось бы.
Пробные прогоны не блокируют боевые. Потом деплой (скил `deploy-hub`).
